01 / Core thesis

核心结论：从搜索热度转向「机会时间差」

新词上涨只是机会的一种表现。更早、往往更可交易的信号，是工具停服、API 改动、迁移受阻、用户重复抱怨、团队公开招聘自动化岗位、公共采购发出需求、产品首次接入收款、政策改变导致流程重做。它们甚至不需要形成一个流行词。

01 · OBSERVE观察变化

谁在什么时候新增、修改、删除、投诉、迁移或付费？

02 · VERIFY收集证据

保存原始链接、时间戳、差异快照；过滤噪音和重复。

03 · INTERPRET还原需求

识别受影响主体、Jobs-to-be-Done、时间压力、付费动机。

04 · DELIVER生成行动

SEO 内容、服务线索、开源任务、迁移方案、垂直工具。

05 · LEARN验证结果

30/60 天追踪使用、回复、销售、修复采纳；迭代权重。

05 / Concrete workflow design

五条可以交给 Agent 执行的工作流蓝图

每条都按 Trigger → Verify → Act → Measure 拆分。点击切换查看具体信号、判定规则、产出结构及 Kill Gate。示例均为设计假设，非已获取的真实线索。

Integration Gap Radar — 从开源生态缺口到可合并 PR 和服务

探测

GitHub Issues / PR、release notes、SDK 官方文档、新模型能力清单；筛 unsupported、not working、Ruby support、streaming、schema、tools。

验证

确认 issue 最近仍开放；对比 RubyLLM Core vs Provider 功能；用测试复现，确认无进行中的竞争 PR。

行动

输出 1 页 Gap Brief：链接、API 示例、测试失败、影响范围、建议扩展接口和 PR 最小修改面。

回测

30 天看 issue 确认、PR 合并、依赖升级、真实开发者复用；不以搜索量为指标。

建议自动筛选规则

优先 2+ 独立来源确认、近期仍活跃、可写自动化回归测试、对 Ruby/Rails 用户有清晰价值；过滤纯询问、重复 bug、与核心维护方向冲突的需求。

Kill Gate

两周内人工精核的前 20 条线索中，少于 3 条可复现、维护者反复表示不愿接收此类贡献，则停止自动扫描该子领域或收窄信号。

Sunset & Migration Radar — 受影响客户窗口比 SEO 窗口更重要

探测

官方终止服务公告、deprecated 字段、API 版本期限、定价页变化、维护者归档 repo。

受影响者

搜索公开依赖线索：GitHub dependents、issue 中受影响场景、授权的自有项目依赖清单；绝不推断私人使用。

行动

迁移地图（旧功能 → 替代功能）、最低风险 PoC、影响日期与升级步骤；针对明确公开 B2B 需求提供定制说明。

回测

观察迁移代码采纳、联系回复、Demo 和付费服务，记录从公告到首次行动的时差。

防误报：计划废弃 ≠ 已终止；存储式快照应保存公告原文、有效日期、适用版本与后续撤回。不要把每次破坏性升级包装成紧急危机。

Website Modernization Radar — 以需求诊断驱动低打扰外联

发现

针对公开商业网站建立目标样本：性能、移动友好、可访问性、失效表单、CMS 版本、信息架构问题。

证据

仅进行合法被动检测和允许的轻量页面检查；双人复核缺陷，记录可复验截图或指标。

预览

创建小范围可审阅的页面原型、性能差异与报价范围；不得复制他人整站或使用未经授权的资产。

销售

依靠公开商务渠道和许可边界低频联系；用回应率、有效会谈和签约率优化。

为什么可持续

大多不依赖「今天的新词」。每周源源不断的网站更新与老化事件可构成常绿市场，关键在买方匹配和交付质量。

Kill Gate

20 个严格合格、人工复核线索中零有效回复，先修改目标行业和价值主张，不增加抓取规模。

Manual Workflow Radar — 从高传播教程挖一个更好的一键工具

识别流程

教程、视频评论、GitHub Discussions、How-to 帖中抽取 3 步以上重复人工任务。

聚类

LLM 将不同说法还原成任务链；由人工确认用户是否真的需要自动化，而不是学习过程本身。

Concierge

不用先开发完整 SaaS；手工执行 5 次，量化耗时、错误与稳定性，再给出自动化原型。

回测

关注是否有重复使用、愿意交付真实任务、付费试用与可观节省；不是教程点赞数。

建议重要的新信号：「解决方案被不断解释」、「评论不断询问能否少几步」、「不同工具之间反复搬数据」，这三者同时出现时强于单个高赞视频。

Fail in Public Radar — 负结果也可成为独特、可核实的内容资产

发现案例

创始人公开 postmortem、停运公告、公开收入/成本复盘、HN/论坛长帖、官方项目归档。

证据标注

按「创始人自述 / 原始文档 / 第三方解读 / 无法核实」分级，建立时间线和声明可信度。

结构化

记录 ICP、问题假设、渠道、定价、时间、关键转折、公开证据；无证据不填写收入或失败原因。

传播回测

生成短帖 + 深度案例页；跟踪保存、引用、纠错、读者订阅。避免将他人经历作为猎奇素材。

治理原则：只整理自愿公开、具有公共相关性的专业案例；不收集私人/敏感信息；区别项目关闭、暂停与个人职业失败；提供更正与删除请求渠道。
06 / Architecture

建议架构：保留 new-term-radar，抽出可复制内核

不要立即把 32 个工作流硬塞进当前 Python CLI。先复制可运行的观察-快照-回测模式做 1–2 个 Radar；等出现 3 条以上重复逻辑再抽公共包。Ruby on Rails 更适合未来销售工作台，Python 继续承担现有扫描作业。

📡

Source Adapters

GitHub、官方 changelog / RSS、HN、站点差分、公开招标 API、用户授权数据。每源单独配额、许可与失败状态。

🧩

Normalized Events

actor · subject · event_type · occurred_at · observed_at · evidence_url · source，区分首次发生与首次看到。

🔗

Entity & Diff Engine

产品 / repo / API / 公司 / 行业 / 任务统一实体 ID；归并别名、增量变化、版本与关系。

🔍

Hypothesis Builder

规则先过滤，AI 再解释 JTBD、影响路径与可能买方；所有重要论断必须链到原始证据。

🎯

Domain-specific Scoring

紧迫性、痛点强度、独立证据、买方可触达性、可交付性、成本与风险。评分可按领域调权。

⚙️

Action Executors

PR 候选、迁移简报、定制审计、内容卡片、报价草案、带人工审核的外联任务。

🗃️

Memory + Provenance

SQLite 作为 V0：实体、事件、证据快照、假设、行动、结果。保留来源抓取时间、hash 与差异。

📈

Outcome Evaluator

SEO 看新曝光；服务看有效回应与成交；开源看 issue 确认与合并；内容看订阅和纠错质量。

🖥️

Workbench + Skills

CLI / MCP 保持轻量。未来 Rails Dashboard 提供证据查看、审核、状态流转和复盘，而非替代采集器。

07 / Metrics and decision discipline

如何判断 Radar 真有用，而不只是不断吐出“有意思”的东西

QUALITY

Precision@20

前 20 条中多少条是人工复核后成立的真实事件/痛点，而非关键词噪声。

ACTIONABILITY

Action@20

前 20 条中多少条能在 2 小时内制定下一步行动，并明确可能买方或维护者。

ECONOMICS

Cost / qualified lead

API、运行、人工复核和生成成本之和 ÷ 有效线索数；不能只算 LLM token。

OUTCOME

30-day impact

PR 合并、迁移委托、会谈、试点付费、内容订阅等；因领域而异。
