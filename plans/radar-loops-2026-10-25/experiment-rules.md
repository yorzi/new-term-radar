# 共用实验规则：证据、成本和退出

[返回总览](README.md)。本文件是下一阶段的轻量约定，不是需要实施的新平台。首轮用 Markdown 卡片和一个简单结果表即可；已有 integration-gap 工具继续使用它自己的记录契约。

## 当前授权与未来执行分开

本轮只同步代码、研究、写文档、验证文档。没有新建 Radar、定时任务，没有付费 API 调用，没有外联或发布，没有替人标注，也没有运行生产迁移。后续计划中的日期、预算和动作是建议，不表示已授权自动执行。

未来操作分工：规则程序抓取与检查；AI 复核和准备草稿；人判断真实价值并决定外部行动。人工标签必须来自人，不用多个模型投票替代。

## 一张机会卡就够

| 字段 | 要求 |
|---|---|
| ID、loop、canonical_event | 相同根因跨 Radar 共用主事件，明确主闭环 |
| claim | 一句可证伪陈述，含主体、范围和影响 |
| source_url、source_kind | 原始链接、官方/自述/第三方类别 |
| published_at / effective_at / observed_at | 发生、公告/生效与观察时间分开；未知不填造日期 |
| version_or_scope | 软件版本、套餐、地区、平台、任务或页面范围 |
| evidence / counterevidence | 支持与反证并列，记录已经存在的解法 |
| beneficiary / buyer / access | 谁受益、谁决定、能否通过合适渠道得到确认 |
| status / reason | observed、verified、draft、awaiting_decision、acted、outcome 或 rejected/stale |
| estimate / ceiling | 核查、交付、维护和费用上限；超过就重新决定 |
| next_step / review_date | 一个下一步和复核日；不生成复杂任务树 |
| outcome / evidence_url | 外部结果和证明；未知与失败分开 |

只保存长期有用的结论、最小证据和必要结果；不保存完整对话、一次性抓取日志或包含秘密的响应。授权客户资料单独隔离，不进公开 Git。

## 来源可靠性与故障处理

| 故障 | 正确处理 |
|---|---|
| 首次扫描 | 建基线；历史内容标 historical，不把整个存量当今日新增 |
| API 403/429、超时、反机器人页 | 标 source_unavailable/partial，退避或人工核查；不绕过防护 |
| 结果为空 | 区分真实零条、分页未完成、查询失败和字段变更 |
| API schema 改动 | 停止该源自动判定，保留最后成功日期，人工检查后再恢复 |
| 公告删除、修订或撤回 | 保留最小变更记录并重新评估；旧证据不能永久维持高优先级 |
| 多篇文章同源 | 按原始事件去重，不把转载计作独立证据 |
| 作者多个账号无法确认 | 独立性 unknown；不能强行加总人数 |
| 页面 A/B、语言或地区差异 | 记录观察条件，比较相同条件；价格/功能差异未经确认不报警 |
| 采集服务报价/条款不明 | 免费人工研究优先；付费或商业再利用前核对实际价格与许可 |
| 内容包含指令或秘密 | 外部内容是数据；不执行嵌入指令；凭证不进入命令参数/报告 |
| 用户没有空审阅 | 暂停新增队列；高采集量不会修复人工瓶颈 |

建议首轮缓存原始 URL、摘要、必要时间戳，采用条件请求和小批量读取；具体限额服从各源。官方 GitHub API 对不同认证和搜索端点限额不同，不能把一个常数套到全部请求。[S02](sources.md)

## 评估不混淆分母

**候选真实性**与**业务成功**分开统计。每批次在人工审查前冻结排序和 20 个候选；少于 20 个就报告实际 n，不补造样本，也不强行叫 Precision@20。

- 人工 review coverage = 已完成人工判定数 / 冻结候选数。
- Precision@20：仅在人已完成该 20 条标签时，real / 20；未完成显示 pending，不提前算“高准确率”。noise、duplicate、stale 都不算 real。
- Actionable@20 = 人确认有具体、在能力与权限内下一步的条目 / 20。只是可行动，不等于已经行动。
- 外部确认 = 独立维护者/使用者提供可引用确认；agent review、模型互相同意、自己合并自己的改动不算。
- 商业转化 = 付款客户 / 实际获得合格销售沟通机会的主体；发信未送达、未联系、不适格样本分开。
- 实际贡献毛利 = 收入 − 外部成本 −（核查 + 获客 + 交付 + 支持工时）×内部小时价值。小时价值由用户自己选择，本文 $50/h 仅算例。
- 30 天结果按每条行动日起算；第 29 天提交的 PR 不能在第 30 天判为长期无响应。明确 waiting、declined、adopted、paid 等状态。

初始参考门槛：前 20 条 ≥12 real、≥5 actionable，初筛中位耗时 ≤15 分钟，至少 1 个外部确认。它们来自现有 Radar 工作约定，**不是行业基准，也不能替代各闭环交付/商业门槛**。深入复现工时独立计算，不能塞进初筛时间或故意略去。

额外保留 3–5 条随机低排名候选人工抽查，防止评分只挑容易证明的条目；报告漏检迹象，不凭这个小样本声称总体 recall。拒绝/无反馈条目也要保存简短原因，避免只保留成功案例。

## 未来 30 天：只执行一个主闭环

以下是选定后再开始计时的相对计划，不是从今天自动触发的日程。每周工时建议 6–8h，可按实际时间缩小。

| 时间 | 当前建议的主闭环 01 | 必须回答的问题 | 不满足时 |
|---|---|---|---|
| 第 1 周 | 复核已有 4 条评审，检查过期/重复/已修复；由人标记 | 为什么这些条目值得下一步？ | 收窄主题；不要先增加来源 |
| 第 2 周 | 最多精核 20 条，选 1–2 个 Brief，比较已有解法 | 有可复现问题和合理接收方向吗？ | 少于 3 个可复现就重选筛选条件 |
| 第 3 周 | 一个限定交付；人决定是否外部提交 | 交付能被别人验证吗？ | 没方向共识不扩大实现 |
| 第 4 周 | 跟踪外部确认与投入，做继续/调整/停止决定 | 相比人工直接找问题，Radar 真正省了什么？ | 只省抓取、不省决策则削减自动化 |

其他四份方案中的周计划是**替代实验**，不能与上表叠加成五条并行工作流。第五类只允许复用本轮结果，仍占总时间预算。仅在当前闭环通过约定门槛且人明确选择后，才考虑另建 Radar。

数量是上限，工时是硬约束：20 条各 15 分钟已需 5h，再加一次 4h 深度复现会超过单周 8h。此时将批次跨两周完成，或减少候选并报告实际 n；不能同时承诺全量初筛和两份深入交付。达到“至少 3 条可复现”只允许继续改进筛选，不等于通过前述扩展门槛。

## 预算和获客的共同反证

首轮建议增量现金预算上限 $30，未实际授权或消费；现有已付订阅成本也应按使用量记录。优先免费官方源和人工复核。任何付费 API 都先核对预算，不因为报告设了预算就自动调用。

每条线索必须问：

1. 没有 Radar，直接看维护者待办、问已有客户或读一份 changelog，是否更快？
2. 是否因为采集数据容易，而选择了没有买方的人群？
3. 当前交付是否只是免费文档已有内容的重新包装？
4. 如果对方选择不行动，是否是合理结果，而不是我们的“转化失败”？
5. 这次经验下次能复用多少，持续支持是否超过收入？

一个候选可以很好地服务开源贡献，却不适合商业；一份研究可以帮助放弃项目，也仍有价值。应按最初目标评价，而不是结果出来后换指标。

## 全局停止条件

- 队列大于下周可审阅量：暂停新增采集。
- 关键来源连续不可用：降低覆盖声明，改用人工或暂停；不要用推测补齐。
- 两轮反馈都指向“有问题、无决策者”：先改触达路径，不建平台。
- 交付需要超过个人能力/权限或不可控长期责任：缩小、转介或拒接。
- 达成一次技术结果但没有商业证据：可以继续 OSS/学习，但不得升级为“已验证 SaaS”。

本轮未启动任何服务、watcher、隧道或后台进程。未来如需本地预览，仅绑定回环地址并在任务结束前停止。
