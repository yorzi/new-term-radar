## 核心假设与切入范围

假设：Ruby/Rails AI 应用在 provider 能力和框架支持之间存在有价值的兼容缺口，Andy 能用比应用团队更低的重复成本解决。只有同时发现“应用需要它”和“当前可行方案不足”才成立；发布了新特性本身不构成机会。

首轮只看 RubyLLM 及少量直接依赖 gem。已有 `/Users/andy/Workspace/OpenSource/radar-integration-gap`，不新建第二个同类扫描器。当前状态见总览：候选不少，外部结果尚未记录。先处理已有评审，再决定是否扩源。

分开两种客户关系：维护者是贡献接收方，企业应用负责人可能是付款方。维护者合并 PR 可验证技术价值，但不能记作销售转化。若没有企业联系，只按 OSS 目标评估，不编造营收预期。

## 最小完整流程

| 阶段 | 输入与动作 | 必须留下的证据 | 退出或分流 |
|---|---|---|---|
| 观察 | 每周至多 2 次看 1 个核心项目、3 个 provider、最多 10 个下游；本轮仅是设计 | release/issue 原链接、发布时间、抓取时间、版本 | API 错误是 source_unavailable，不能输出“无缺口” |
| 去重 | 以能力/根因 + provider + 版本范围归并；同一公告在多站转载算一次 | 主事件 ID、关联 issue/PR | 上游补丁和下游升级属于关联动作，不重复计两个独立机会 |
| 核实能力 | 对照当前稳定版、main、文档、插件和进行中 PR | 支持矩阵及准确 Git SHA | main 已修复 → 等 release/验证下游；不再开相同 PR |
| 核实影响 | 指定 Ruby/Rails/provider/model/API 版本和实际调用 | 最小复现、预期/实际行为、测试条件 | 无真实需求仅收藏；版本旧但没阻塞 → 排除 |
| 判断归属 | 核心共性、provider 扩展、应用特例或文档缺口 | 路由原因与维护边界 | 纯配置问题写说明；应用特例不塞进核心 |
| 准备交付 | 先写失败用例，再做最小修复及兼容说明 | 本地补丁、回归结果、限制和 PR 草稿 | 维护者方向未知时先提讨论草稿，不大规模实现 |
| 人工决定 | 人决定是否提交、联系、认领 | 外部行动链接及日期 | 没发布保持 draft；AI 不代填人工 label |
| 跟踪 | 7/14/30 天核对确认、发布和实际采用 | issue/PR/release/用户确认链接 | 无回应是 unknown，不是 reject；合并后未发布单列 |

GitHub 和 RubyGems 可提供观察材料，但只覆盖各自可见范围。普通版本更新已有 Dependabot，竞争差异应是 **行为兼容、失败复现、迁移语义与应用验收**。[S01–S04](sources.md)

## 一页 Compatibility Brief 的内容

1. **谁被影响**：具体版本、运行环境和任务；实际已确认用户与推测用户分开。
2. **缺了什么**：provider 原始能力说明；当前框架处理路径和 SHA；不支持证据。
3. **复现**：最小输入、预期/实际输出、错误、测试命令；mock 与 live 分开。
4. **现有选择**：配置修复、插件、已有 PR、等待 release、暂不升级；说明为何仍需新补丁。
5. **方案**：修改面、兼容风险、测试矩阵、回退、维护者接收信号。
6. **结果**：人工标签、行动链接、合并/发布/采用状态；如涉及服务，单列付款和工时。

Brief 初筛不超过 15 分钟；通过后才投入 2–4 小时深度复现。无法在预算内确认的条目标为 needs_research，不能因已花时间而继续扩大范围。

## 必须处理的分支

| 情况 | 判断与行动 |
|---|---|
| gemspec 限制旧主版本，但没有运行故障 | 不说“用户被困住”；先检查约束意图、已发布版本和实际升级测试 |
| lockfile 旧，gemspec 已允许新版 | 这是应用锁定状态，未必是 gem 维护问题；查真实使用方是否需要升级 |
| 新能力仅 beta、特定账户/区域开放 | 标清权限；不把无法访问当框架 bug；无法做 live 测试保留未知 |
| 核心支持，但官网遗漏或模型目录陈旧 | 分流文档/目录更新；不实施重复适配器 |
| 流式路径失败，非流式成功 | 测试 chunk 顺序、取消、工具调用组合，不能只通过 happy path |
| provider 行为变化但 SDK 还没更新 | 以官方协议和可重复行为为准；SDK 发布只是信号，不是唯一事实源 |
| 维护者已有方向或有人认领 | 补测试/复核现有方案；尊重重复劳动成本，不抢提同一补丁 |
| 无维护者响应或项目稳定但长期无发布 | 不直接贴 abandoned 标签；等待 14 天后最多一次人工决定的跟进，30 天归档 |
| 修复要求账户密钥或收费 API | 报告离线验证边界；后续需明确授权和限额才做付费复现 |
| 测试需执行陌生 gem/脚本 | 先读代码和依赖，按该仓库约束获取授权，不因“开源”默认可信 |
| 高风险安全问题 | 转为已授权防御修复；不公开复现敏感目标，不扩成主动攻击服务 |
| 一个根因牵涉很多下游 | 优先修根因；按独立用户和实际采用计数，不以 PR 数扩大成果 |

## 交付与商业路径

先提供一个可合并补丁或可采纳迁移说明。后续若企业主动提供真实问题，再销售有边界的兼容审计/迁移：例如一个应用、一个 provider、一个主要流程，交付回归用例、变更说明和回退手册。持续支持、其他 provider、生产故障响应另定义。

获客假设：公开贡献被真实使用后，使用者可能提出定制需求；这是待测渠道，不保证发生。更直接的证据是现有联系人主动提供项目及预算。不开自动评论、自动 PR 或群发流程。

以内部工时值 $50/h 作示例：复现 3h、实现测试 5h、沟通 2h、支持预留 2h，加 $20 直接成本，总成本 $620；报价 $900 时剩 $280，再扣未计获客成本。此算例说明“小 PR”也可能没有服务利润，不是建议统一报价。实际时薪、预算和税费另核对。

## 实验与停止条件

- 第 1 周：复核现有 4 条已评审未标注候选；重新查当前版本，由人标记 real/noise/duplicate/stale。
- 第 2 周：最多精核 20 条，产出至多 2 个深入 Brief；至少 1 个可复现、维护方向合理的交付候选才继续。
- 第 3–4 周：仅在用户决定外部行动后观察反馈；目标是至少 1 次独立维护者/用户确认，不预设一定合并。
- 若前 20 条少于 3 条可复现，先缩窄 provider/问题类型；连续两轮仍如此则停止新增采集。
- 若补丁可用但无人采用，记录为技术产出，不宣称市场成立。若 30 天有 OSS 价值却无买方，可继续作为贡献活动，但停止收入预期。
- 不用已陈旧的 102 条作成功率分母。采用统一的固定批次、标签和观察窗口，规则见 [实验规则](experiment-rules.md)。

**结束判据：** 一个真实问题被验证，交付被外部接受或明确拒绝，原因回写筛选规则。仅生成 Brief 不算闭环完成。
