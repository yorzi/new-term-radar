# 03 · 重复手工任务 → 人工代办 → 稳定自动化

[返回总览](README.md) · Atlas 10/11/18/31/32；15/19 只辅助发现人群。

## 具体切口与反命题

先聚焦小型软件团队/代理商的一个重复交接任务，例如“把多个来源的客户反馈整理成待人工确认的 issue 草稿”。这是**待验证示例**，不是已发现需求；也不自动执行客户沟通或发 issue。

用户是执行任务的人，买方通常是团队负责人；两者可能对“省时间”的价值判断不同。必须说明节省的时间能否用于有价值工作，是否减少错漏、延误或返工。自动化若只是把复制粘贴换成校验 AI 错误，价值可能为负。

竞争基线是现有脚本、原生集成、Zapier、n8n，以及继续人工。通用连接能力已广泛存在。若原生方案满足要求，推荐配置服务或直接使用它；无需重新开发产品。[S11/S12](sources.md)

|---|---|---|
| 教程/多工具链（10/32） | 提取步骤、输入输出、人工检查点 | 步骤多一定值得一键化 |

一条 canonical task 应写成：“某岗位在某触发下，拿到什么输入，必须在何时得到什么输出，不能违反什么约束，失败损失是什么”。“自动化营销”“AI 报表”都太宽。

## 首轮取样与证据门槛

限定一个岗位、一个任务，人工阅读最多 30 条近 90 天公开材料。起步来源优先项目官方 Discussions、公开教程和 HN；YouTube 可用官方评论接口；Reddit 接入与商业使用资格需单独核对，不作为唯一关键来源。[S13/S17/S18](sources.md)

公开数据只能用于提出假设。至少 3 个独立使用者描述同一输入输出约束，再邀愿意参与者提供经授权脱敏样本。相同作者的跨平台发帖、教程作者自己的评论、转载和营销帖不能算独立用户。高热度是可见性，不能替代频次与损失。

复用 `asks`/`pains` 的候选提取思路，但不直接采用其搜索量门槛作为 B2B 任务入选规则；低搜索量也可能有价值。`one_click` 的教程/点赞规则只用于排序，不承担真实性判断。[L3](sources.md)

## 从代办到自动化

1. **观察一次原过程**：记录真实总时长、工具切换、等待、失败和人工判断。敏感信息由用户遮蔽；不录取无关数据。
2. **手工代办五次**：覆盖不同日期/输入，保留输出由用户验收。一次演示不能代表重复稳定性。
3. **查替代**：用同一验收标准尝试原生配置、现有脚本/连接器；如果够用，结束产品假设，转交配置方案。
4. **自动化一个高重复环节**：先做可审阅草稿，不直接写生产系统。确定性映射用代码；语义判断才交模型。
5. **与手工基线比较**：比较总工时和正确性，包括检查、重试、修正、接入、维护，不只比较按钮运行时间。
6. **第二位用户试用**：使用相同核心流程；如需重写大半规则，则是定制服务，不是已成立的通用产品。
7. **形成付费范围**：按任务量、输入格式、支持周期限定；试用转付费、付款、续用分别记录。

## 最小产品边界

仅实现一个输入格式、一个主要输出、一个可见状态页或报告、人工确认、可重试/可撤销策略。不给首轮增加多租户、插件市场、任意工作流编辑器和全自动代理。

假设示例：反馈文本/CSV → 去重、保留原引用 → 按团队规则生成 issue 草稿 → 人确认 → 导出。验收是保留来源、无编造事实、字段正确、不会丢反馈；“摘要听起来不错”不够。

| 场景 | 要求 |
|---|---|
| 重复输入、超时后重试 | 有稳定任务 ID 和幂等键，不能重复创建真实记录 |
| 一个步骤成功、后续失败 | 明确已完成部分，从检查点恢复；不让整链盲目重跑 |
| 时间/货币/编码/分页差异 | 测试跨时区、空值、超长文本、非 UTF-8 输入、分页尾部；不静默截断 |
| AI 判断置信度不足 | 转人工并显示原文，不靠自报 confidence 当真实概率 |
| 输入包含提示注入 | 将文档内容视为数据；不能指挥工具授权、发送消息或改变系统规则 |
| OAuth 到期或权限不足 | 任务明确 blocked，保留重试入口；不请求不必要权限 |
| API 改版/限流 | 固定契约测试、退避、来源状态提示；无结果不等于没有任务 |
| 无法撤销的业务动作 | 默认人工确认；为失败设计补偿或明确拒绝全自动化 |
| 只有浏览器 UI、无稳定 API | 单独评估维护成本和条款；不承诺稳定产品，必要时保留人工流程 |
| 包含客户隐私 | 明确哪些数据发送给哪个处理方、保存多久；无权限用合成数据验证 |
| n8n 编辑器嵌入产品 | 官方 OEM 文档要求商业协议；不能把开源可见误读为任意嵌入免费 [S12] |
| 人工是质量关键步骤 | 保留人工；“少一步”不是必须达成的目标 |

## 可计算的收益

每次净节省 = 原过程分钟 − 自动化操作分钟 − 检查分钟 − 重试/返工分钟。月净价值 = 任务次数 × 每次净节省 / 60 × 用户认可的小时价值 − API/工具费 − 月维护工时价值。

算例（假设）：每周 10 次、每次从 20 分钟降到含检查的 8 分钟，四周约节省 8h；若客户认可 $30/h，则毛价值 $240。减 $30 工具费、2h 维护即 $150。若再收 $200/月，则客户净收益为负，不能以“节省 60% 时间”掩盖问题。首次接入 4h 还须按真实使用月数摊销。

服务方也要计算：接入、异常处理、账号支持和更新所耗时间。一个客户一个格式的定制服务可以盈利，但不要因此宣称存在可复制 SaaS。

## 验证计划与停止条件

- 第 1 周：30 条材料最多收敛 3 个候选任务；选一个，写清当前替代。
- 第 2 周：目标 3 名独立用户确认；没有人愿提供脱敏真实任务，不做产品原型。
- 第 3 周：手工完成 5 次，取得任务成功定义；再开发至多 1 天的最小自动化。
- 第 4 周：两名用户累计至少 10 次任务；报告成功次数/总次数、耗时中位数与最差一次，而非只展示最佳视频。
- 建议继续门槛：净工时减少 ≥30%、关键错误 0、至少一人愿再次使用并有明确付费讨论。该门槛是设计起点，任务本身有风险时提高要求。
- 三位用户约束无法合并、原生方案足够、接入成本超过合理回收期、连续两轮返工吞掉收益：停止产品化，保留服务或撤销方向。
- 拒绝重复使用优先于口头赞赏；免费试用率和付费率分开。

**结束判据：** 同一任务在真实场景重复完成并产生净收益，或证伪后停止。五个漂亮 demo 不是五次真实使用。
