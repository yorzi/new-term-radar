# 04 · 网站关键流程问题 → 小范围修复 → 可验证交付

[返回总览](README.md) · Atlas 20；9/27 可辅助。以 Rails/Hotwire 范围为优先，不把“网站老旧”当可销售证据。

## 从泛重构收窄

广泛扫描网站、生成审计、群发改版样稿，很容易优化出“报告很多、客户很少”的系统。买方购买的是重要任务更可靠、后续更好维护，而不是抽象的现代感。

建议首个 ICP：已有联系人或代理商转介的 Rails 小型 B2B 产品，存在一个已报告的注册、询价、预约或账户管理问题。使用者报告问题，负责人确认优先级，代码/部署权限可获得。若只能看到公开主页，最多做初步观察，不能承诺修好内部流程。

备选 ICP 是技术栈可控的小型服务网站，但需要重新核实交付能力。不能因会 Rails 就默认能经济地改所有 WordPress、Shopify 或专有 CMS。

## 为什么先修流程而非重建

完整重构同时改变内容、导航、URL、分析、表单和部署，扩大验收与回滚成本。单一路径修复可证明交付能力，也更容易判断买方是否认可价值。现有主题设置、现有代理商和简单内容修正都是优先比较对象。

设计三层判断：

1. **观察事实**：特定设备/浏览器/登录状态下发生了什么。
2. **用户影响**：哪类用户的哪个任务受阻；性能、无障碍、内容可理解性分别记录。
3. **商业优先级**：负责人是否认为值得修、是否有预算；不从页面表现推导营业额损失。

PageSpeed 实验室数据和现场数据不同；页面缺 CrUX 样本可能退到 origin 或没有现场数据。自动化无障碍工具也不能完成全部判断。[S08–S10](sources.md)

## 流程与最小交付

| 阶段 | 动作与产物 | 验收边界 |
|---|---|---|
| 找对象 | 优先已明确求助、转介或现有客户；最多 10 个样本 | 没有采购路径的站点只记技术观察 |
| 被动观察 | 首页 + 一个关键路径，记录 URL、环境、时间及截图 | 不提交真实表单、不创建账户、不扫描漏洞；深入检查需站点授权 |
| 人工复核 | 同一问题至少复现两次；如有条件让第二人复核 | 第二个 AI 结论不能代替真实用户/辅助技术验证 |
| 诊断卡 | 一页列 1–3 个问题、影响、复现、建议、未知项 | 不输出几十页通用审计或“必然违法”判断 |
| 范围确认 | 一个模板/路径、设备矩阵、必要集成、验收人、变更窗口 | 未知代码质量先做发现阶段，不报无上限固定价 |
| 修复/预览 | staging 或本地 demo，用授权或自有资产 | 预览不是生产；不能拿 mock 数据当客户效果 |
| 验收 | 同条件复测，表单/业务回归、键盘和适用辅助技术检查 | 范围外页面未测；分数提升不等于业务转化提升 |
| 交接 | 变更记录、部署/回退、遗留项、维护约定 | 7/30 天确认任务是否继续可用；转化须有足够真实样本 |

## 合格线索的最低字段

`website / owner_role / reported_problem / reproduction / affected_task / stack_confidence / business_priority / permission / next_step`。

若 stack_confidence 为低，不根据 HTML 特征武断识别后端版本；若 owner_role、business_priority 未确认，不进入报价队列。页面好不好看不是硬门槛。

样例（合成）：一个 Turbo 表单错误后焦点回到页首，键盘用户不能找到错误消息。修复包括错误 summary、字段关联、焦点和返回操作；验收覆盖首次提交、服务端错误、重复提交、浏览器后退。只有拿到真实授权页面后才能确认该问题存在，当前不对应任何客户。

## 异常和责任边界

| 情况 | 处理 |
|---|---|
| Lighthouse 分数波动 | 固定设备/网络/测试条件重复测量，报告分布；不选择最好的一次 |
| CrUX 无数据或只有 origin | 显式标注缺失/粒度，不能把全站数据贴成单页数据 |
| 机器人保护导致“表单失效” | 先与真实用户和站点负责人核对；不把自动化受阻当客户故障 |
| 第三方嵌入不可改 | 分析替换、外围修复或明确豁免；不能保证供应商组件被完全修复 |
| 只有公开页面权限 | 不点击实际购买/提交，不测试后台；诊断限制写进范围 |
| 有真实支付/邮件副作用 | staging 使用测试配置；生产验证由客户指定方式和授权执行 |
| 自动检测无问题 | 不等于无障碍完成；按约定范围做人工键盘/辅助技术检查 |
| 客户需要法规符合性证明 | 技术修复与专业符合性评估分开；未具备资质/能力不承诺法律结果 |
| 改版牵涉 URL/SEO | 保留路径、重定向及 sitemap 方案，测试重要入口；不承诺排名提升 |
| 旧系统无测试或部署脆弱 | 先评估备份/恢复与隔离环境；无法安全回退就不直接动生产 |
| 低流量无法证明转化 | 只承诺任务可用性和技术验收；业务改善保持未验证 |
| 客户实际想整站换风格 | 重新定义设计项目，不把它算作已验证的技术修复线索 |

## 商业实验

提供一个限定路径的诊断和修复，不免费为每个陌生站点设计完整首页。报价将发现、修复、跨环境回归、交接和短期支持计入；内容录入、第三方订阅、整站设计、超范围模板不默认包含。

假设 8h 修复验收 + 4h 沟通支持，内部 $50/h，加 $20 工具费为 $620。报价 $900 时余 $280；若免费为 20 个站点各花 30 分钟准备 demo，另有 $500 获客工时，即使成交一单也亏损。**因此优先关系和明确意向，而不是扩大扫站。** 该算例不是市场价格。

渠道优先级：已有客户 → 代理商转介 → 明确公开求助 → 经用户决定的少量定制联系。发送行为不在当前授权任务内，也不由 Radar 自动触发。

## 验证和停止

- 第一周只选一个细分人群、最多 10 个网站/产品；拿到至少 2 个负责人问题确认才准备深入方案。
- 第二周形成 1–2 份具体诊断卡；零确认则调整渠道，不增加扫描量。
- 第三周完成一个有授权的限定 demo 或 staging 修复；它验证交付可行性，不代表成交。
- 第四周观察付费诊断/修复接受、验收与后续支持时间。没有业务数据不报告转化率提升。
- 后续若累计 20 个合格且实际获得沟通机会的对象均无有效反馈，停止该 ICP/价值主张。没送达、没授权联系者不能混入“20 个拒绝”。
- 支持负担超出收费、第三方系统不可控或没有安全部署条件：收窄/拒接；不要用更大重构解决销售不成立。

**结束判据：** 指定路径完成约定验收，客户确认，遗留风险和支持责任交接；技术与商业结果分别记录。
